# 구독 관리 — 남은 작업 정리

> 리팩터링 완료: 실행 상태(쿼타/잔량)가 Organization으로 이동됨.
> Subscription은 빌링 이력 + 스냅샷 역할만 담당.

---

## 1. Consume 연결 (크레딧/스토리지 실제 차감)

`repo.consume_credits()`, `consume_storage_mb()`, `release_storage_mb()` 함수는 만들었지만 호출부 없음.

- **크레딧 차감**: AI 사용 완료 후 `org_repo.consume_credits(db, org_id, cost)` 호출 연결
  - `preview_mapping`에서 `check_credit_quota`(읽기 체크)는 하지만 실제 차감이 없음 → `plan_credits_remaining`이 항상 초기값 유지
  - 차감 시점: LLM 호출 성공 후 (실패 시 차감하면 안 됨)
  - `read_only=True` 트랜잭션에서는 차감 불가 → 트랜잭션 전략 재검토 필요
- **스토리지 차감**: 파일 업로드/삭제 흐름에 `consume_storage_mb` / `release_storage_mb` 연결
  - bytes → MB 변환 정책: `math.ceil(file_size / 1_000_000)`? 아니면 누적 후 변환?
  - 하이워터마크 vs 현재값: 현재 설계는 현재값(삭제 시 회수) 방식

## 2. 기간 갱신 (자동 갱신 / 만료 처리)

`current_period_end`가 지나도 아무 일도 안 일어남. 스케줄러 없음.

- 갱신 로직: 기존 구독 `expire()` → 새 구독 생성 → org의 `plan_credits_remaining` 리셋
  - STARTER(무료): 자동 갱신 — 스케줄러 or lazy 체크
  - 유료 플랜: 결제 성공 후 갱신 (결제 연동 후)
- `bonus_credits_remaining`은 리셋하지 않음 (감소만)
- `used_members`, `storage_mb_used`는 리셋하지 않음 (누적 상태)
- 스케줄러 vs lazy: 스케줄러가 명확하지만, lazy(요청 시 만료 체크)가 구현 단순

## 3. 구독 중단 정책 (CANCELED / PAST_DUE / EXPIRED)

상태 전이 메서드만 존재, 처리 정책 미정.

- **CANCELED**: 기간 끝까지 서비스 허용 (업계 표준)
  - `cancel_at_period_end = True` 설정 → 기간 종료 시 갱신 차단
  - 쿼타 체크는 org 컬럼 기준이므로 subscription 상태와 무관하게 동작 (기존 이슈 해소됨)
- **PAST_DUE**: 결제 실패 유예 기간 (7일? 14일?)
  - 유예 중 서비스 허용 여부
  - 유예 후 EXPIRED 자동 전환
- **EXPIRED**: 서비스 차단 범위
  - 읽기 전용(데이터 열람만) vs 완전 차단
  - 데이터 보존 기간: 일정 기간 후 삭제? 영구 보존?

## 4. 플랜 변경 (업그레이드 / 다운그레이드)

미구현. plan_type 변경 + org 캐시 컬럼 동기화 필요.

- **업그레이드**: org의 `max_members`, `plan_credits_remaining`, `storage_mb_limit` 즉시 반영
  - 크레딧: 차액만 추가? 새 플랜 한도로 리셋?
  - 새 구독 생성 + 기존 구독 expire
- **다운그레이드**: 기간 종료 시 적용 (즉시 적용 시 초과 상태 문제)
  - TEAM(20명) → STARTER(5명)인데 현재 15명: 기존 멤버 유지, 추가만 차단
  - `cancel_at_period_end` 유사하게 `pending_plan_type` 컬럼으로 예약?
- **월 ↔ 연 전환**: 기간 종료 시 전환 (프로레이션 없음)
  - "다음 결제일부터 전환됩니다" — Notion, Linear 방식

## 5. 결제 연동

PG 연동 전까지 STARTER(무료) 전용.

- PG 선택: Stripe (글로벌) / 토스페이먼츠 (국내)
- 결제 실패 시 `PAST_DUE` 전환 → 재시도 → 유예 후 `EXPIRED`
- 인보이스 / 영수증 발행
- 웹훅 처리 (결제 성공/실패/환불)

## 6. 보너스 크레딧 구매

`bonus_credits_remaining` 컬럼은 있지만 구매 플로우 없음.

- 1회성 크레딧 팩 구매 → `bonus_credits_remaining` 증가
- 나중에 `credit_purchases` 테이블 추가 시 이 컬럼이 SUM 캐시 역할
- 결제 연동(5번) 선행 필요
