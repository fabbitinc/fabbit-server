# Service Conventions

## 목표

- Service를 재사용 가능한 비즈니스 연산 계층으로 유지하라.
- 서비스 계약은 도메인 타입 중심으로 설계하라.
- 이 스킬은 Service 규칙만 다루고 다른 레이어 세부 규칙은 다루지 마라.

## 네이밍 규칙

- 클래스: `*Service`
- 메서드명: 도메인 동사 기반 (`create`, `update`, `changeRole`, `archive`)
- 입력/출력: 도메인 타입(Entity/VO/ID/enum/원시값) 중심

## 레이어 규칙

- Service는 여러 시나리오에서 재사용 가능한 업무 연산을 제공하라.
- Service 메서드 시그니처에 웹 계층 타입(`*Request/*Response`)을 넣지 마라.
- 파라미터가 과도하게 많을 때만 서비스 전용 `*Input/*Output`을 도입하라.
- 서비스는 도메인 규칙을 명시적으로 표현하라.
- 인프라 기술 세부사항 노출을 서비스 계약으로 끌어올리지 마라.

## 도메인 의존 및 이벤트 방식 규칙

- Service는 자기 도메인의 `Repository`만 기본 참조하라.
- Service에서 다른 도메인의 `Service/Repository`를 직접 참조하지 마라.
- 타 도메인 경계 타입(`*Api/*Policy`)은 interface/class 중 팀 합의된 한 가지 방식으로 일관되게 사용하라. interface를 강제하지 않는다.

## 적용 절차

1. 서비스가 제공할 도메인 연산을 먼저 확정하라.
2. 메서드명을 도메인 동사로 명명하라.
3. 입력/출력을 도메인 타입 중심으로 설계하라.
4. 파라미터가 길어질 때만 `*Input/*Output` 도입 여부를 판단하라.
5. 서비스 계약에서 웹/문서화 타입 의존성을 제거하라.

## 빠른 체크리스트

- 클래스명이 `*Service`로 끝나는가?
- 메서드명이 도메인 동사를 반영하는가?
- 서비스 시그니처에 `*Request/*Response`가 없는가?
- 서비스 전용 `*Input/*Output`은 필요한 경우에만 쓰는가?
- 서비스가 재사용 가능한 비즈니스 연산으로 구성됐는가?
- 타 도메인 접근이 `*Api/*Policy` 경계로만 이뤄지는가?
